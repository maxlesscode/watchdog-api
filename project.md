# Watchdog — Project Overview

## What is Watchdog?

Watchdog is a price-monitoring service. You give it a list of products (with their web page URLs and a price threshold), and it automatically watches those pages for you. When the actual price of a product drops to or below your threshold, it sends you an email alert so you can act before the price goes back up.

Think of it as a personal shopping assistant that never sleeps and never misses a deal.

---

## What problem does it solve?

Checking prices manually is tedious. You have to remember to visit each page, and prices can change at any hour. Watchdog eliminates that burden: once a product is registered, the system checks its price every hour on its own and notifies you automatically — no browser open, no spreadsheet to update.

---

## How does it work? (step by step)

1. **You register a product** via the API — you provide its name, the URL of its web page, and the target price you are willing to pay.
2. **Every hour**, Watchdog visits each product page, reads the price shown on it, and records it.
3. **If the price is at or below your target**, Watchdog sends an email to the configured alert address.
4. To avoid flooding your inbox, alerts are sent **at most once every 24 hours** per product, even if the price stays low.

---

## What data is stored?

Two tables live in the database.

### Products table

Each row represents one product you are tracking.

| Column | What it means |
|---|---|
| `id` | Unique internal number for the product |
| `name` | Human-readable name you gave it (e.g. "Sony WH-1000XM5") |
| `url` | The exact web page address where the price is visible |
| `actual_price` | The most recently scraped price |
| `target_price` | The price at or below which you want an alert |
| `price_selector` | Optional CSS hint telling the scraper exactly where on the page the price lives |
| `last_checked_at` | When the price was last fetched |
| `last_alerted_at` | When the last email alert was sent (used to prevent spam) |

### Price history table

Every single price reading is also logged here, so you can later see how a product's price evolved over time. Each row is one reading: which product, what price, at what time. If a product is deleted, all its history is deleted too.

## Key design choices and why

### Plain HTTP, no heavy framework
The service uses only Go's built-in HTTP library and a lightweight router. This keeps the binary small, removes unnecessary complexity, and makes the behaviour completely predictable. There is no hidden magic — every request path can be followed line by line.

### No ORM — raw SQL queries
Database queries are written directly in SQL, not generated by an ORM (an object-relational mapper). This gives exact control over what gets sent to the database, avoids surprising queries, and makes performance issues easy to diagnose.

### PostgreSQL as the database
PostgreSQL is a mature, battle-tested open-source relational database. It was chosen for its reliability, support for timestamps with time zones (important for scheduled tasks), and its `ON DELETE CASCADE` feature that automatically cleans up price history when a product is removed.

### Schema migrations, not manual table creation
The database tables are created and updated via *migration files* — versioned SQL scripts that run in order on startup. This means the schema is always reproducible: any new environment starts with exactly the right tables, and future changes are applied safely without data loss.

### Two-strategy price extraction
When visiting a product page, the scraper first looks for a standardised machine-readable price (called **JSON-LD schema.org**), which many e-commerce platforms embed for search engines. If that is not present, it falls back to the `price_selector` field you can optionally provide. This two-step approach means many products work out of the box, and the selector is only needed for sites that do not follow the standard.

### Resilient scraper with retries and a circuit breaker
A website can be temporarily slow or return an error. Rather than giving up immediately, the scraper:
- **Retries up to 3 times** with increasing wait times between attempts (1 s, then 2 s).
- **Stops trying a domain** for 5 minutes after 5 consecutive failures. This avoids hammering a broken site and wasting resources.

### 24-hour alert deduplication
If a product's price stays below the target for multiple consecutive checks, you would otherwise receive an email every hour. The `last_alerted_at` timestamp prevents this: after an alert is sent, the next one for the same product can only go out 24 hours later.

### API key authentication
Every request (except the health check) must include a secret key in the `X-API-Key` header. This ensures only authorised callers can read or modify your product list.

### Per-IP rate limiting
To protect against abuse, the API limits how many requests any single IP address can make per second (configurable via environment variables). Clients that exceed the limit receive a "too many requests" response.

### Email alerts via SMTP
Notifications are sent through standard SMTP (the same protocol mail clients use). No third-party notification service is required — just point the system at any SMTP server. If no SMTP credentials are configured, the notification system is simply disabled and the rest of the service continues to work normally.

### Structured logging
All log lines are written in a machine-readable format (key-value pairs) rather than plain English sentences. This makes it straightforward to search, filter, and pipe logs into monitoring tools. In development mode, logs also appear in the terminal.

### Health check endpoint
`GET /health` returns the current server status and whether the database is reachable. This endpoint is intentionally not protected by the API key so that monitoring tools can call it without credentials.

## Security choices

- **No private URLs**: When you register a product, the URL is validated. It cannot point to a private or internal network address (e.g. `192.168.x.x`). This prevents the service from being used to probe your internal infrastructure.
- **Constant-time key comparison**: The API key check uses a technique that takes the same amount of time regardless of whether the key is correct or not. This closes a subtle attack where an attacker could guess the key character by character by measuring response times.
- **Header injection prevention**: Email subject lines and bodies are sanitised to strip special characters that could trick email clients into misreading the message structure.

## Deployment overview

```
[Your API client]
        │  HTTP + X-API-Key header
        ▼
  :9999  Watchdog API
        │
        ├── PostgreSQL database  (port 5432)
        │       products table
        │       price_history table
        │
        └── Background scheduler (every hour)
                │
                ├── visits product URLs
                ├── extracts prices
                ├── saves price history
                └── sends email if price ≤ target
```

The service and its database are started together with a single `docker compose up -d` command. An Adminer database browser is also started on port 8080 for inspecting data directly.
